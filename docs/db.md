# forge::db: SQLite, shard sets and parallel search

Headers under `support/include/forge/db/`; link `forge::db` (CMake target `forge_db`: header-only code over the static library `forge_sqlite`). `#include <forge/db/shards.hpp>` pulls in the whole layer. Tests: `test_db`, `test_db_parallel`, `test_db_shards`, `test_cache`, `test_gpu_ann_logic`, `test_task_algorithms`, `sqlite_pin`. Example: `docs/examples/db_search.cpp` (ctest `doc_example_db_search`). Benchmarks: `perf/bench_db.cpp`, `perf/bench_vfs.cpp`. ANN: [ann.md](ann.md).

## Vendored SQLite

`third_party/sqlite/` holds the unmodified amalgamation of SQLite **3.54.1** (`sqlite3.c`, `sqlite3.h`, `sqlite3ext.h`), downloaded from `https://www.sqlite.org/2026/sqlite-amalgamation-3540100.zip`. `PIN` records the version, the URL, the SHA3-256 that sqlite.org publishes for the zip (`92281c86e2957f9b9305890f9ac04204caa7b677cc868dc326d942689df28e30`, compared with the download on 2026-11-18), a SHA-256 of the zip (`0a9c8e34...e6ad1f9`), and the SHA-256 and SHA3-256 of each of the three files. ctest `sqlite_pin` (`cmake/check_sqlite_pin.cmake`) recomputes them. SQLite is public domain; it is listed in `NOTICE` and in the SBOM (`tools/sbom.py`).

`forge_sqlite` (static, C99, warnings silenced on this target only) is built with FTS5, RTREE, JSON (built in), `SQLITE_THREADSAFE=2`, `SQLITE_DQS=0`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`, `SQLITE_OMIT_DEPRECATED`, `SQLITE_DEFAULT_WAL_SYNCHRONOUS=1`, `SQLITE_USE_ALLOCA`, and two more: `SQLITE_MAX_ATTACHED=125` (bulk load) and `SQLITE_OMIT_LOAD_EXTENSION` (no `dlopen`, so it builds the same on every CI platform). `test_db` (`sqlite_build_options`) reads them back through `PRAGMA compile_options`. CI (PR 74, 18 Nov) built and ran it on Linux (GCC, Clang, ASan, TSan), MSVC, MinGW, macOS, iOS, FreeBSD and Android; the failures were tests that also fail on main (`test_compress`, `compress_import`), plus `test_os_net` once on linux-clang (a network test).

## The wrapper (`db/sqlite.hpp`)

```cpp
auto c = db::connection::open("a.db", {.wal = true, .synchronous = "NORMAL"});   // open_options: read_only, immutable, uri, busy_timeout_ms, cache_size_kib, mmap_size, pragmas, sorter_threads...
c.exec("CREATE TABLE t(id INTEGER PRIMARY KEY, name TEXT, v BLOB)");
{ db::transaction tx(c); auto ins = c.prepare("INSERT INTO t(name, v) VALUES(?, ?)"); ins.run("a", blob); tx.commit(); }
auto st = c.prepare("SELECT id, name FROM t WHERE id > :lo"); st.bind(":lo", 0);
for (auto& r : st.rows()) use(r.get<std::int64_t>(0), r.get<std::string_view>(1));
auto [n] = c.query_row<std::int64_t>("SELECT count(*) FROM t");
```

Typed `bind` and `get<T>` (integers, bool, floating point, strings, `std::span<const std::byte>` blobs, `std::optional<T>` for NULL; `static_text`/`static_blob` bind without a copy), `transaction` (rolls back unless committed; a transaction inside a transaction is a savepoint), `connection::try_open` (returns `forge::result`), `integrity_check()`, `attach/detach`. Every failure throws `db::error`, a `forge::forge_exception` whose `errc` is mapped from the SQLite code (`busy`/IO/cantopen to `io_error`, corrupt to `integrity_error`, not-a-database to `format_error`, nomem to `out_of_memory`, constraint/misuse/range to `invalid_argument`, SQL syntax to `parse_error`) and which carries the primary and extended SQLite codes and the SQL text. One connection is used by one thread at a time (`SQLITE_THREADSAFE=2`).

FTS5 helpers (`db::fts5`): `create`, `rebuild`, `optimize`, `integrity_check`, `words`, `quote_phrase`, `query_from_text` (every word quoted, so FTS5 operators in user text are harmless), `search` (k best by `-bm25()`, ties by rowid).

## Parallel layer (`db/parallel.hpp`, `task/algorithms.hpp`)

`read_pool` (N read-only connections to one file), `rowid_partitions` / `range_sql` (fixed rowid ranges, `rowid BETWEEN :lo AND :hi`), `parallel_map`, `parallel_query`, `parallel_scan`, `parallel_filter`, `parallel_reduce`, `parallel_sort` (per-partition stable sort, then the stable parallel merge), `parallel_topk` and `parallel_bm25_topk` (order: score descending, id ascending), `parallel_bulk_load` (one staging database per partition filled in parallel, then `ATTACH` and `INSERT ... SELECT` in partition order inside one transaction: the target gets the same rows and rowids as a serial loop). Partitions are fixed by the caller, partition results are combined in partition order, and ties never depend on timing, so **every function returns exactly the serial result for any pool size**. `task/algorithms.hpp` holds the pieces: `parallel_sort` (stable, equals `std::stable_sort`), `parallel_merge` (co-ranking, stable), `merge_runs`, `parallel_topk_by`, `parallel_reduce`, `parallel_inclusive_scan` / `parallel_exclusive_scan` (fixed blocks, so floating-point results also do not depend on the thread count; they equal the serial run of the same blocked algorithm, not a plain left fold). `pool == nullptr` runs serially on the caller.

Checked (`test_task_algorithms`, `test_db_parallel`): sort, merge, k-way merge, top-k, reduce and scans, and query, scan, filter, reduce (integer and double), top-k, bm25 top-k, sort and bulk load, each compared with the serial result for 1, 2, 3, 8 and 16 threads on fixed-seed data (30000 rows with gaps in the rowids and many equal scores), and for two different partition counts. Not provided: a parallel index build (SQLite has one writer per database; `open_options::sorter_threads` sets `PRAGMA threads` for SQLite's own sorter).

## Shard sets: the default storage (`db/shards.hpp`)

A database is a directory:

```
lean.db/manifest.json      small text: schema version, per-shard {file, key range, rows, bytes, sha256, blake3}, caller statistics
lean.db/shard-000000.fdb   a SQLite file of at most 10 MiB, rows sorted by key
lean.db/shard-000001.fdb   ...
```

`db::open(path)` gives a `shard_set` (a plain SQLite file gives a one-shard set; `db::open_single` / `connection::open` is the explicit single-file path for small or temporary databases). `db::create` / `shard_writer` writes one.

**Layout is the search structure.** Shards hold consecutive key ranges, so `shard_set::shards_for_key / shards_for_range / shards_for_prefix` binary-search the manifest and a lookup opens only the shard(s) whose `[min, max]` can hold the answer. Everything else (`shard_map`, `shard_query`, `shard_range_query`, `shard_topk`, `shard_bm25_topk`, `ann::shard_ann`) runs over a list of shards on `forge::task` and combines results in shard order or by a total order, so results never depend on the thread count.

**Writing** (`shard_writer`): rows (`std::vector<db::value>`, the key column a string or bytes, stored as a BLOB so keys compare as `memcmp`) arrive presorted (streamed in waves of `wave_bytes`, 256 MiB by default) or in any order (buffered, then stably sorted with `task::parallel_sort`). The first shard of the first wave is built to calibrate file bytes per raw byte; the rest are cut to 90 % of the budget by that ratio and built in parallel; each file is finalised (`page_size` 4096, `journal_mode=DELETE`, `VACUUM`, `user_version`) and **checked on its final size**: over the budget, it is split in halves and rebuilt (a single row larger than the budget is an error). `shard_schema::finalize` runs inside each shard before `VACUUM` (fill the FTS5 table, save an HNSW graph, ...). Builds are byte-reproducible: for the same rows, schema, hook and options the shard files and the manifest are identical bytes for any thread count (`test_db_shards`, `reproducible_budgeted_builds`: SHA-256 of every shard and the manifest text compared across 1, 2, 3, 8 and 16 threads, several waves). The manifest is written with `os::fs::write_file_atomic`; shard files are renamed into place.

**Opening** (`shard_set`): the manifest is parsed and its key ranges checked; each shard is verified (size, BLAKE3 and SHA-256) the first time it is opened (`verify_mode`; `verify_all(pool)` checks all now); a mismatch throws `errc::integrity_error` naming the shard. Shards open read-only with `immutable=1` (no locking, no journal files), `mmap_size` = the shard size and a 1 MiB page cache, so a query on a warm shard is served from the page cache through the mapping. Connections are pooled per shard; `max_open_bytes` (1 GiB by default) bounds the shards that keep open connections, least recently used closed first. A shard missing from `<dir>` is looked for in `blob_dir` (by SHA-256) and then in `shard_open_options::cache`, a `forge::cache::store` (by BLAKE3).

**I/O: prefetch and placement (`db/shard_io.hpp`).** `run_options::kind` chooses the prefetch: `none`; `fadvise` (`posix_fadvise(WILLNEED)` per shard, POSIX only; **the default, `automatic`**); `aio` (a background thread reads the shards of the query in 1 MiB chunks at queue depth 32 through `forge::io::async_reader`, io_uring on Linux and a pread pool elsewhere, discarding the bytes so the page cache holds them; a shard is read once per set, `shard_set::mark_prefetched`, and files that `mincore` reports resident are skipped). `aio` is opt-in because of a measured failure, see "Measured". `run_options::schedule`: `dynamic` (default), `blocked` (contiguous runs), `numa` (shards split into one contiguous run per NUMA node from `os::numa_nodes()`, a worker takes from the node of its CPU and steals from the next node when its run is empty; `placement_stats` counts own and stolen shards; the node layout and the worker's node can be injected for tests). Placement changes who runs a shard, never a result (`test_db_shards`, `prefetch_kinds_and_numa_schedule_return_the_plain_result`: every kind x 5 thread counts x cold/warm, and NUMA over a fake two-node layout, equal to the plain run). This machine has one NUMA node, so a NUMA gain could not be measured; the schedule is correct and tested, not shown to be faster.

**Hashes.** The manifest keeps SHA-256 per shard (`forge::hash::sha256`, new: what git and external pins use) and BLAKE3 (the library's own hash, the one `forge::cache` keys on; two to three times cheaper per byte to check, and the one the cache layer uses). Both are checked on open by default. The BLAKE3 of the manifest text is `shard_set::id()`.

**Content-addressed storage and cache.** `shard_options::blob_dir` additionally keeps each shard as `<blob_dir>/<sha256>.fdb` (hard link, else copy), and `shard_open_options::blob_dir` falls back to it when `<dir>/<file>` is missing: a shard built or fetched once is reused by every database and version that lists the same hash (`test_db_shards`, `verification_and_content_addressed_store`). **Shards in `forge::cache`**: `shard_options::cache` also puts every shard into a `cache::store` as a raw file (no header; `store::put_file`/`get_path`, [support.md](support.md#cache-forgecache)) keyed by its BLAKE3, `shard_open_options::cache` reads it back (verified like any shard), and a second database with the same shard bytes adds no entries, so shards are reused across versions and share the store's byte budget and LRU order (`shards_live_in_forge_cache`). Query results can be kept in the same kind of store with `cached_result(store, set, {query parts}, compute)`, keyed by `set.id()` plus the query, so a rebuilt database never serves a stale answer; `encode_hits/decode_hits` serialise `shard_hit` lists.

**Exact BM25 over shards.** FTS5's `bm25()` takes its statistics from the table it runs on, so a shard alone scores differently from the whole. `shard_bm25_topk(set, pool, "fts", terms, k)` scores every shard with the global statistics through a registered FTS5 auxiliary function `forge_bm25(fts, avgdl, idf_blob, weights...)`, which is FTS5's own formula (k1 = 1.2, b = 0.75, same arithmetic, same order) with the average document length and per-term IDF passed in: `N` (rows) and total tokens come from the manifest (`shard_info::fts_rows/fts_tokens`, written when `shard_schema::fts_table` is set), each term's document count is the sum over the shards. The ranking and the scores are bit-identical to `bm25()` on one table holding all the rows (`test_db_shards`, `bm25_over_shards_equals_unsharded`: 8 queries x OR/AND x k in {1, 10, 100} x 5 thread counts x pruning on/off against the unsharded table, comparing ids and exact doubles; also weights, and a one-shard set). The `fts` table's rowid must carry the global id.

**Phrases.** A term may be a multi-word phrase (`"w12 w7x"`; `fts5::quote_phrase` makes it one FTS5 phrase). Its document count comes from a `count(*) ... MATCH` query on each shard that may hold it, and its score is `bm25()`'s for that phrase; `phrases_over_shards_equal_unsharded` compares 17 phrase queries (phrase alone, phrase + words, a phrase that matches almost nothing, upper case, punctuation between the words) x OR/AND x k x 2 thread counts x filters on/off with the unsharded table: ids and exact scores equal. Limit: the document-count shortcut and the term filters assume FTS5's default tokenizer (`unicode61`); a table with another tokenizer (porter, trigram) must be written with `df_table = false` and `bloom_bits_per_term = 0`.

**Per-term counts and term filters.** Each shard stores its per-term document counts (`forge_df`, from `fts5vocab`, `shard_options::df_table`), read by primary key for plain ASCII words (lower-cased, as the default tokenizer does); other terms use the `count(*) ... MATCH` query. With `shard_options::bloom_bits_per_term` (10 by default, 0.35 % false positives measured) every shard also gets a bloom filter over its terms, all kept in one sidecar file `terms.fbl` named, sized and hashed (SHA-256, checked on first use) in the manifest and byte-identical for any thread count. A negative answer is exact (the term is in no row of the shard), so the count phase of a query does not open a shard that cannot hold any query term: its row and token totals come from the manifest and its counts are zero. A positive answer only means "ask the shard"; non-ASCII terms and phrases with no ASCII token are always "maybe", a phrase needs every one of its tokens present. `bm25_report` has `counted` (shards opened for counts), `with_hits`, `scored`, `skipped_bound`; `bm25_options::bloom = false` turns the filters off. Results are equal with and without (`bloom_filters_are_exact_and_skip_counts`: no false negative over every term of every shard, 7 query shapes x OR/AND x k x 2 thread counts equal to the unsharded table, equal `df`; in that test a rare-term query opened 10 of 27 shards; a damaged `terms.fbl` is an `integrity_error`, a missing one means the exact path).

**Early stop.** A term adds less than `(k1 + 1) * idf` to a row, so a shard whose matching terms sum below the current k-th best score cannot contribute. Shards are scored in descending order of that bound and skipped when it is strictly below the k-th score. The result never changes (`prune` on and off are compared in the test); `bm25_report` says how many shards were skipped. Rates on the benchmark queries are under "Measured".

**ANN.** One HNSW graph per shard, saved inside the shard; see [ann.md](ann.md#ann-over-shards-annshard_annhpp) for why and for the measured recall. A batched exact search on a GPU is in [ann.md](ann.md#gpu-batch-search-annpugpu_flathpp-graphann_gpuhpp).

**Not adopted, with the measurement.** (1) *A FORGE VFS over `core/mapped.hpp`*: `perf/bench_vfs.cpp` registers a minimal read-only VFS (xFetch into a `forge::map_readonly` mapping) and compares it with the default VFS at `mmap_size` = file size on one 9 MiB shard, best of 15 to 25: point lookups 14.8 against 14.5 us (9p) and 1.41 against 1.42 us (tmpfs), full scan 2.9 against 2.7 ms and 2.8 against 2.7 ms, FTS5 query 13.0 against 13.7 ms and 6.51 against 6.53 ms; opening 9.2 against 11.5 ms (9p, noise) and 248 against 233 us. No gain, so SQLite's own mmap is used. Without any mmap (`pread`) point lookups are 15x slower on 9p (219 us) and 1.7x slower on tmpfs. (2) *FORGE's arena/tlsf allocators*: a graph search makes 23 to 26 heap allocations (counting `operator new`), about 1 us of 500 to 1300 us per query; an arena for the candidate heaps of `search_layer_` showed no consistent difference in 40-run best-of timings on this loaded host (differences of both signs, up to 40 % between runs of the same binary), so it is not used. The BM25 hot path is SQLite's, and its per-shard top-k heap is one `reserve` per shard.

## Measured

**Status of this section: incomplete.** The 18 to 19 Nov benchmark run on the 2.2 GB data set exposed a defect in the first version of the `aio` prefetch (below), which made every sharded timing meaningless; the default was changed to `fadvise` and each shard is read by `aio` once per set (`mark_prefetched`), but the benchmark could not be re-run because the WSL VM crashed (`Wsl/Service/E_UNEXPECTED`) before the fix could even be compiled. What follows is only what the run established independent of timing: sizes, build times, result equality, pruning counts, the aio finding and the single-file timings. **No sharded-versus-single-file speed claim is made.** The earlier 1M-row numbers (0.56 GB, previous commit) are not repeated here: they were taken with the old code and a quarter of the data. To reproduce: `bench_db --dir D:/scratch/dbbench2 --rows 3600000 --reuse` after building with `-DFORGE_BUILD_DB_BENCH=ON` (the data build is `--build-only`).

**Machine and caveats.** One WSL2 VM, 64 logical CPUs (Xeon Gold 6242, one NUMA node), 47 GB, load average 40 to 65 from unrelated jobs during every run, data on a Windows drive mounted into WSL (9p), GCC 13 `-O2`, all niced. On this 9p mount `posix_fadvise(DONTNEED)` does not drop anything and `mincore` reports 0 resident pages even for mapped files; a fresh mapping re-faults every page from the host at about 47 us per 4 KiB page (a 9 MiB shard: 0.12 s every time it is mapped anew, measured also for the second and third touch), while a connection that stays open keeps its mapping. So "cold" in the tables means "fresh handles", not an empty page cache, and nothing here says how a native disk behaves.

**Data.** `perf/bench_db.cpp`, synthetic: 3,600,000 rows, a 12 to 35 word text body from a skewed 4000-word vocabulary, a clustered term `c<i/40000>` in every third row of its id range (2 to 3 shards each), a unique-ish term `u<i/200000>` in about 1 row of 20011, a 32-d Gaussian float vector, key = 8-byte big-endian id. Each shard holds the rows, an FTS5 index (contentless), the per-term counts and an HNSW graph (M = 16, efConstruction = 100); the single file holds the same rows and index and one global graph with the same parameters. **2.2 GB**: 255 shards, 2241.8 MiB (with graphs; the term filters add one sidecar file) against one file of 2227.7 MiB. Build: sharded 847 s on 8 threads; single file 579 s for rows and index (serial insert) plus 1801 s for the global graph on 8 threads (both while a full build and a test run shared the machine).

**Result equality** (checked inside the benchmark, a mismatch aborts it): point lookups, prefix scans (51200 rows both), the scan total, and the BM25 top-10 of the first 8 queries of every class against `bm25()` on the unsharded table (ids and exact scores): equal in all six query classes and all three sharded variants (filters + pruning, no filters, neither).

**BM25 pruning rates** (100 queries per class, top-10, 8 threads; 255 shards; counts are means per query; the times of this run are not quoted, see above):

| class | variant | shards opened for counts | shards with a term | shards scored | skipped by bound |
|---|---|---|---|---|---|
| frequent words (2 to 3 terms, OR) | default | 255 | 255 | 255 | 0 |
| clustered rare term (1 term) | term filters | **4.6** | 3.8 | 3.8 | 0 |
| | no term filters | 255 | 3.8 | 3.8 | 0 |
| rare + 2 frequent words (OR) | default | 255 | 255 | **137.2** | **117.8** |
| | no filters, no pruning | 255 | 255 | 255 | 0 |
| rare AND frequent | default | 255 | 3.9 | 3.9 | 0 |
| unique term + frequent word (OR) | default | 255 | 255 | **58.6** | **196.4** |

(The "rare AND frequent" filter row opens 255 shards because the frequent word is in every shard and its count is needed; the AND then scores only the 3.9 shards that hold the rare term. The phrase class did not run: the run ended inside the unique-term class when the VM died.) So the filters remove the count phase for a single rare term (4.6 of 255 shards opened instead of 255; before the filters the previous benchmark skipped 0 shards on frequent-word queries and still does: nothing can be skipped when every shard holds every term), and the score bound skips 46 % of the shards for a rare term OR-ed with frequent words and 77 % with a unique term. The previous benchmark's "0 shards skipped" is explained by its all-frequent queries, as stated then.

**The aio defect.** With `aio` as the default prefetch, every query read every shard it touched again, because `mincore` cannot see the page cache of a 9p file (it said 0 resident, always), so nothing was ever "already resident": 2.2 GB per full query at about 160 to 190 MB/s through io_uring (queue depth 32; sequential `read()` of the same files: 10 MB/s host-cold, about 100 MB/s host-warm) = **13.6 s per BM25 query** and 17 ms per point lookup (a 10 MiB read per lookup), against 2.5 s per query for the single file. Measured with `aio_prefetcher` alone, aio at depth 32 does read 20 shards at 186 MB/s against 100 MB/s sequential (the files were host-warm), so on this file system it is the better way to *read*, but the bytes do not stay in a guest page cache, so reading them ahead gains nothing when each mapping re-faults anyway. Fixes made: the default is `fadvise`; `aio` reads a shard once per set. Not re-measured.

**Single file (valid timings, per operation, 100 queries unless noted; the single file has no prefetch).** Point lookup: 125 ms at 1 thread (the first touches of a file that is not cached), 3.2 ms at 4 threads, 2.7 ms at 8 and 2.4 ms at 16 (cold), 2.2 ms at 16 threads warm. Prefix scan of about 256 keys: 183 to 231 ms at every thread count. BM25 top-10 on frequent words (8 queries, 64 rowid partitions): 15.9 s at 1 thread, 2.3 s at 4, 2.4 s at 8, 2.7 s at 16 (cold); 1.5 s at 16 threads warm. Full scan `sum(length(body))`: 60 s at 1 thread cold, 13.7 s at 4, 20 s at 8, 17 s at 16. These come from a loaded host and a 9p mount: do not read the 4/8/16-thread differences as scaling.

**Not measured:** a quiet machine, a native disk, repeated runs (no spread), the sharded layout after the aio fix (everything above for it is void), the I/O section (prefetch kinds and schedules cold and warm), the ANN recall-against-ef frontier for per-shard graphs against the global graph (the global graph of 1801 s build exists; the comparison did not run), the phrase class, NUMA effects (one node), `max_open_bytes`, shards served from `forge::cache`. The previous run's ANN observation stands only as a warning: a global graph with M = 8 and efConstruction = 64 reached recall 0.39 on 1M vectors, which says that graph was badly tuned, not that sharding is better.
